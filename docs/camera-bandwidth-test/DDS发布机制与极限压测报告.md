> 测试时间: 2026-07-07
> 测试环境: W1 机器人, PC1 (Jetson Orin NX, 192.168.20.20) + PC2 (192.168.20.21)
> 网络链路: 千兆 (1000 Mbps), PC1 LAN0 MTU=1500, PC2 LAN1 MTU=9000
> ROS2 Humble + CycloneDDS, ROS_DOMAIN_ID=20, auto 模式运行中

## 一、DDS 发布底层原理

### 1.1 消息发布的数据路径

ROS2 使用 CycloneDDS 作为 RMW 实现，发布消息时的数据流：

```
发布端 (kfc_camera)                              订阅端 (w1_act / recorder)
┌──────────────────────┐                        ┌──────────────────────┐
│ 1. 用户 publish(msg) │                        │ 5. 网卡收到 UDP 包    │
│ 2. DDS CDR 序列化    │  ── 千兆网络 ──>        │  6. DDS CDR 反序列化  │
│ 3. 拷贝到发送缓冲区   │                        │ 7. 回调 cb(msg)       │
│ 4. 网卡分 UDP 包发送  │                        │                      │
└──────────────────────┘                        └──────────────────────┘
```

### 1.2 序列化开销

CycloneDDS 对每条消息做 CDR（Common Data Representation）序列化：

- Image 消息：1.56MB → 序列化需拷贝整个 data 数组 + header 元数据
- CompressedImage 消息：0.44MB → 序列化拷贝 data 数组（已是压缩后的，体积小）

序列化本质是**内存拷贝**，CPU 密集。帧越大，单次序列化开销越高。

### 1.3 多订阅者的开销来源

| 开销来源       | 说明                                 | resize (1.56MB)              | compressed (0.44MB)         |
| -------------- | ------------------------------------ | ---------------------------- | --------------------------- |
| CDR 序列化     | 每帧序列化一次，与帧大小成正比       | 1.56MB × 27Hz = 42 MB/s     | 0.44MB × 27Hz = 12 MB/s    |
| 发送缓冲区拷贝 | 每个跨机订阅者触发一次发送缓冲区写入 | 每个订阅者 +1.56MB           | 每个订阅者 +0.44MB          |
| UDP 分包       | 大消息需拆成多个 UDP 包（MTU=1500）  | 1.56MB ÷ 1500 ≈ 1040 包/帧 | 0.44MB ÷ 1500 ≈ 293 包/帧 |
| QoS 历史缓冲   | KEEP_LAST depth=2，维护历史帧        | 2 × 1.56MB = 3.12MB 缓冲    | 2 × 0.44MB = 0.88MB 缓冲   |

### 1.4 为什么 resize 降频而 compressed 不降频

**根因：发布端 CPU 序列化开销，不是网络带宽**

证据：

1. **ping 延迟不恶化**（始终 < 7ms）：网络本身没堵
2. **topic hz 下降**：发布端来不及按 27Hz 节奏发布
3. **帧越大开销越大**：resize 1.56MB 的序列化开销是 compressed 0.44MB 的 3.5 倍

发布端（kfc_camera）是单线程发布，序列化+发送是串行的。多订阅者时：

- resize 4 个订阅者：序列化 + 4 × 发送拷贝 = 4 × 1.56MB × 27Hz = 168 MB/s CPU 拷贝 → CPU 跟不上
- compressed 5 个订阅者：5 × 0.44MB × 27Hz = 59 MB/s CPU 拷贝 → CPU 轻松

## 二、网络带宽上限分析

### 2.1 链路规格

| 参数                   | PC1 LAN0          | PC2 LAN1          |
| ---------------------- | ----------------- | ----------------- |
| 链路速率               | 1000 Mbps（千兆） | 1000 Mbps（千兆） |
| MTU                    | 1500              | 9000              |
| 理论带宽上限           | 125 MB/s          | 125 MB/s          |
| 实际可用（扣协议开销） | ~117 MB/s         | ~117 MB/s         |

### 2.2 各场景带宽消耗

| 场景              | 单帧   | 频率 | 单订阅者带宽 | N订阅者总带宽 | 占千兆比       | 是否超限       |
| ----------------- | ------ | ---- | ------------ | ------------- | -------------- | -------------- |
| resize 1订阅      | 1.56MB | 27Hz | 42 MB/s      | 42 MB/s       | 36%            | 否             |
| resize 4订阅      | 1.56MB | 27Hz | 42 MB/s      | 168 MB/s      | **143%** | **超限** |
| compressed 5订阅  | 0.44MB | 27Hz | 12 MB/s      | 60 MB/s       | 51%            | 否             |
| compressed 12订阅 | 0.44MB | 30Hz | 13 MB/s      | 156 MB/s      | **133%** | **超限** |

### 2.3 带宽 vs CPU 瓶颈

| 话题       | 先遇到哪个瓶颈                 | 原因                                                          |
| ---------- | ------------------------------ | ------------------------------------------------------------- |
| resize     | **CPU 序列化**先成为瓶颈 | 4订阅时 CPU 拷贝 168MB/s，但带宽 168MB/s 也超限，CPU 先扛不住 |
| compressed | **带宽**先成为瓶颈       | 12订阅时 CPU 拷贝 156MB/s 可接受，但带宽 156MB/s 超千兆上限   |

### 3.4 理论极限验证

compressed 单帧 0.44MB，30Hz 发布：

- 单订阅者带宽：0.44MB × 30Hz = 13.2 MB/s
- 千兆网上限：~117 MB/s
- 理论极限订阅者数：117 ÷ 13.2 ≈ **8.9 个跨机订阅者**

实测 12 个本地订阅者仍稳定（本地不走网络，走共享内存/进程内），13 个开始断流。

- 本地订阅者极限 ~12 个（CPU 序列化瓶颈：12 × 0.44MB × 30Hz = 158 MB/s CPU 拷贝）
- 跨机订阅者极限 ~9 个（带宽瓶颈：9 × 13.2 = 119 MB/s ≈ 千兆上限）

## 四、综合结论

### 4.1 降频根因总结

| 话题                         | 降频根因                         | 证据                                           |
| ---------------------------- | -------------------------------- | ---------------------------------------------- |
| resize (Image)               | **发布端 CPU 序列化开销**  | ping 不恶化但 hz 下降，帧大导致 CPU 拷贝跟不上 |
| compressed (CompressedImage) | **网络带宽**（超12订阅时） | 13订阅断流，理论带宽 156MB/s 超千兆 117MB/s    |

### 4.2 compressed 极限

| 场景     | 极限订阅者数 | 瓶颈       | 说明                              |
| -------- | ------------ | ---------- | --------------------------------- |
| PC1 本地 | ~12 个       | CPU 序列化 | 12×0.44MB×30Hz=158MB/s CPU 拷贝 |
| PC2 跨机 | ~9 个        | 网络带宽   | 9×13.2MB/s=119MB/s ≈ 千兆上限   |

### 4.3 实际部署结论

dexe_recorder 只新增 1 个订阅者，远低于极限：

- compressed 现有 2 个订阅者 + recorder 1 个 = 3 个，远低于 12 个极限
- resize 现有 1 个订阅者 + recorder 1 个 = 2 个，但 resize 2 个就开始降频

**compressed 有充裕的余量，resize 没有余量。这进一步验证了应选 compressed。**

### 4.4 带宽上限

| 链路         | 速率      | 实际可用  | compressed 可承载 | resize 可承载                |
| ------------ | --------- | --------- | ----------------- | ---------------------------- |
| PC1-PC2 千兆 | 1000 Mbps | ~117 MB/s | ~9 个跨机订阅者   | ~2 个跨机订阅者（CPU先瓶颈） |
