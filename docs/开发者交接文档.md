## 一、项目概述

`dexe_recorder` 是一个 ROS2 C++ 节点，用于 **auto 模式（自主导航 + ACT 推理）下的数据采集录制**。它订阅机器人状态、相机图像、末端执行器等话题，将数据保存为视频（H.264）或图片（JPEG），并生成与遥操录制格式兼容的 `pose_record.json` 和 `metadata.jsonl`，便于后续转换为 HDF5 训练数据。

**与遥操录制的关系**：遥操（`dexe_teleoperate`）用 Python 录制数据，auto 模式用本 C++ 节点录制，两者产物目录结构一致，共用同一套 HDF5 转换脚本。

## 二、快速启动

### 2.1 编译

```bash
cd /home/dexforce/w1/dexe_recorder
./build.sh
# 或手动：colcon build --cmake-args -DCMAKE_BUILD_TYPE=Release
```

### 2.2 运行

```bash
source /opt/ros/humble/setup.bash
source /home/dexforce/w1/install/setup.bash
source /home/dexforce/w1/dexe_recorder/install/setup.bash
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
export ROS_DOMAIN_ID=20

ros2 run dexe_recorder dexe_recorder_node
```

节点启动后会自动加载 `~/w1/dexe_recorder/config/auto_recorder.yaml` 配置文件。

### 2.3 服务接口

推荐用 `recorderctl.sh`（自动 source 环境，PC1/PC2 通用）：

```bash
cd ~/w1/dexe_recorder/scripts        # PC1
# 或 cd ~/workspace/dexe_recorder    # PC2

./recorderctl.sh start    # 开始录制
./recorderctl.sh stop     # 停止录制
./recorderctl.sh status   # 查询状态
```

也可直接用 ros2 命令（需先 source ROS2 环境）：

```bash
# 开始录制
ros2 service call /dexe_recorder/start_recording std_srvs/srv/Trigger

# 停止录制
ros2 service call /dexe_recorder/stop_recording std srvs/srv/Trigger

# 查询状态
ros2 service call /dexe_recorder/get_status std srvs/srv/Trigger
```

## 四、代码逻辑

### 4.1 整体架构

```
                    ROS2 话题订阅
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
   OnState (100Hz)  OnCompressedImage  OnImage (30Hz)
   关节JSON解析      (27Hz 头部JPEG)    手部raw Image
          │              │              │
          ▼              ▼              ▼
     FrameBuffer（有界队列，满了丢最旧帧）
          │
          ▼
     WriterLoop（独立线程）
     ├── 写 pose_record JSONL
     ├── 写 metadata.jsonl
     └── GstRecorder.PushFrame()
               │
               ▼
     GStreamer Pipeline（硬件加速）
     ├── nvjpegdec 解码
     ├── videocrop 左右目拆分
     ├── nvv4l2h264enc 硬编（video模式）
     └── filesink / multifilesink
```

### 4.2 核心类

#### `RecorderNode`（recorder_node.h / recorder_node.cpp）

主节点类，继承 `rclcpp::Node`。

**订阅话题：**

- `/feedback/robot_server_state`（std_msgs/String）：100Hz 关节状态 JSON，含 `joint_position`（反馈）和 `joint_position_cmd`（指令）
- `/camera/kfc_compressed`（sensor_msgs/CompressedImage）：27Hz 头部相机，3840×1080 左右目并排 JPEG
- `/camera_l/color/image_rect_raw`、`/camera_r/color/image_rect_raw`（sensor_msgs/Image）：30Hz 手部相机
- `/control/ee/left`、`/control/ee/right`（end_effector_interfaces/EEJointControl）：15Hz 末端执行器

**服务接口：**

- `~/start_recording`（std srvs/Trigger）：开始录制，创建 session 目录，初始化 GStreamer pipeline
- `~/stop_recording`（std srvs/Trigger）：停止录制，flush pipeline，合并 pose JSON
- `~/get_status`（std srvs/Trigger）：查询录制状态

**录制流程：**

1. `StartRecording()`：生成 session ID（时间戳），创建目录，打开 pose_file/metadata_file，初始化 GstRecorder，启动 WriterLoop 线程
2. 话题回调将数据推入 `FrameBuffer`（关节帧）或直接推入 `GstRecorder`（相机帧）
3. `WriterLoop()` 线程从 buffer 取帧写 pose JSONL + metadata
4. `StopRecording()`：停止 buffer，join 线程，GstRecorder.Stop()（发 EOS flush pipeline），合并 pose JSONL 为 JSON

#### `GstRecorder`（gst_recorder.h / gst_recorder.cpp）

GStreamer pipeline 管理器，负责相机数据的硬件加速编解码。

**三条独立 pipeline：**

1. **Head pipeline**：appsrc → jpegparse → nvjpegdec → nvvidconv(NVMM→sysmem) → tee → [videocrop 左/右] → nvvidconv(sysmem→NVMM) → nvv4l2h264enc → qtmux → filesink
2. **Hand left pipeline**：appsrc → nvvidconv → nvv4l2h264enc → qtmux → filesink
3. **Hand right pipeline**：同上

**关键方法：**

- `Start(session_dir, format)`：初始化 GStreamer，创建三条 pipeline，设为 PLAYING 状态
- `PushCompressedFrame(data, size)`：推入一帧 kfc_compressed JPEG 数据
- `PushHandFrame(camera_name, data, size, w, h, encoding)`：推入一帧手部相机 raw Image
- `Stop()`：向各 appsrc 发 EOS，等 pipeline flush 完成，销毁 pipeline

#### `FrameBuffer`（recorder_node.h / frame_buffer.cpp）

线程安全的有界队列，生产者-消费者模型。

- `Push(Frame&&)`：非阻塞，满了丢最旧帧并计数
- `Pop(Frame*)`：阻塞等待，返回 false 表示停止
- `Stop()`：唤醒所有等待的消费者

### 4.3 数据产物

录制一个 session 后的目录结构：

```
data/recorded_auto/20260707_120000/
├── head/
│   ├── left/
│   │   └── video.mp4          # video模式：H.264 1920×1080
│   │   └── 000000.jpg ...     # jpeg模式：1920×1080 JPEG
│   └── right/
│       └── video.mp4 / *.jpg
├── hand/
│   ├── left/
│   │   └── video.mp4 / *.jpg
│   └── right/
│       └── video.mp4 / *.jpg
├── pose_record_20260707_120000.json   # 关节数据（tele兼容格式）
├── pose_record_20260707_120000.jsonl.tmp  # 临时文件（stop后合并为json）
└── metadata.jsonl                      # 每帧元数据（时间戳、帧号、相机类型、路径）
```

## 五、关键技术点

### 5.1 GStreamer Pipeline 设计

**头部相机（kfc_compressed）**：

- 输入：3840×1080 左右目并排 JPEG
- `nvjpegdec` 硬件解码输出 NVMM 内存
- `nvvidconv` 将 NVMM 转为系统内存（video/x-raw,format=I420）
- `videocrop` 软件裁切左半（left=0, right=1920）和右半（left=1920, right=0）
- `nvvidconv` 再转回 NVMM 给 `nvv4l2h264enc` 硬件编码
- `qtmux` 封装为 MP4

**为什么不能直接用 `videoconvert`**：`nvjpegdec` 输出 NVMM 内存，软件 `videoconvert` 无法访问，必须用 `nvvidconv` 做内存转换。

**为什么手部相机不需要拆分**：手部相机是独立 Realsense D405，每个相机本身就是单目，无需 videocrop。

### 5.2 VIDEO 与 JPEG 两种模式对比

两种模式**都是边录制边落盘**（GStreamer pipeline 实时处理），不是录完才写。每帧推入 appsrc 后，GStreamer 内部线程自动完成解码→裁切→编码→写盘。

**共同的前半段（完全一样）**：

```
appsrc(JPEG) → jpegparse → queue → nvjpegdec(硬解) → nvvidconv(NVMM→sysmem) → tee
                                                                              ├→ videocrop(左) → 编码 → 落盘
                                                                              └→ videocrop(右) → 编码 → 落盘
```

**后半段差异**：

|                      | VIDEO 模式（默认）                  | JPEG 模式                      |
| -------------------- | ----------------------------------- | ------------------------------ |
| **编码器**     | `nvv4l2h264enc`（GPU 硬编 H.264） | `nvjpegenc`（GPU 硬编 JPEG） |
| **封装**       | `qtmux` → MP4 容器               | `multifilesink` → 逐帧文件  |
| **落盘方式**   | 连续写入单个 video.mp4              | 每帧写一个 000xxx.jpg          |
| **I 帧间隔**   | 每 30 帧一个 I 帧（帧间压缩）       | 每帧独立（都是"I 帧"）         |
| **单文件大小** | ~68MB/12s（bitrate 4Mbps）          | 383张 × ~130KB ≈ 50MB/12s    |
| **编码速度**   | 极快，~2ms/帧（P 帧只编码差异）     | 快，但每帧独立全量编码         |
| **IO 效率**    | 高（顺序写单文件）                  | 较低（每帧 open/write/close）  |
| **stop 延迟**  | 1-2 秒（qtmux 需写 MP4 moov atom）  | 几乎无延迟（每帧已独立写完）   |

**实测数据（12 秒录制，kfc_compressed ~27Hz）**：

- VIDEO：1128 帧，0 丢帧，head/left/video.mp4 = 68MB
- JPEG：1247 帧，0 丢帧，head/left/000000.jpg~000382.jpg 各 ~130KB

**结论**：VIDEO 模式整体更快（帧间压缩 + 顺序 IO），JPEG 模式优势在 stop 时无延迟且单帧可独立查看。默认用 VIDEO。

### 5.3 ⚠️ 重要踩坑：OpenCV 与 GStreamer 冲突

**绝对不要在此 C++ 节点中引入 OpenCV（`#include <opencv2/...>` 或调用 `cv::` API）！**

详见 [GStreamer-OpenCV冲突踩坑记录](GStreamer-OpenCV冲突踩坑记录.md)。简要结论：

- C++ 源码中包含 `cv::` API 调用会导致 OpenCV 共享库在 `main()` 之前加载
- OpenCV（opencv4tegra）的 `.init_array` 初始化与 `nvjpegdec` 的 NVMM 硬件资源初始化冲突
- 触发 SIGBUS（Bus error），GDB 调用栈完全损坏
- Python（遥操）不受影响，因为 Python 解释器的加载环境不同
- **解决方案**：所有图像处理在 GStreamer pipeline 内完成，不依赖 OpenCV

### 5.4 分辨率参数

- kfc_compressed 实际分辨率：**3840×1080**（左右目并排）
- 拆分后每目：**1920×1080**（横向）
- 代码中 `input_width = 3840`，`half_w = 1920`，切勿改为 1920/960

### 5.5 关节状态 JSON 解析

`/feedback/robot_server_state` 是 JSON 字符串，关键字段：

- `joint_position`：关节反馈位姿（float64 数组）
- `joint_position_cmd`：实际指令位姿（融合了 tele/ACT/上位机输入）
- `joint_velocity` / `joint_velocity_cmd`
- `joint_torque` / `joint_torque_cmd`
- `timestamp`：纳秒时间戳

一个话题同时提供 control + feedback，无需分别订阅多个话题做时间戳对齐。

### 踩坑记录

1. **OpenCV 与 GStreamer 冲突** → 详见 [GStreamer-OpenCV冲突踩坑记录](GStreamer-OpenCV冲突踩坑记录.md)
2. **x264enc 属性名**：`speed-preset`（不是 `speedpreset`）
3. **NVMM 内存**：nvjpegdec 输出 NVMM，软件 element 无法直接处理，需 nvvidconv 转换
4. **kfc_compressed 分辨率**：实际是 3840×1080（不是文档中部分写的 1920×1080）5. **tar 解压丢失可执行权限**：`install.tar.gz` 解压后 `dexe_recorder_node` 变成 `-rw-rw-r--`（无执行权限），`ros2 run` 报 `No executable found`。deploy.sh 已加 `chmod +x` 自动修复
6. **install.tar.gz 路径嵌套**：包内结构是 `install/dexe_recorder/...`，解压到 `~/workspace/install/` 会变成 `install/install/`。需注意解压目标，或手动 `cp -r` 修正
7. **`The passed service type is invalid`**：新终端未 source ROS2 环境就执行 `ros2 service call`。另外服务类型是 `std_srvs/srv/Trigger`（下划线连写），不是 `std srvs/srv/Trigger`（有空格）。用 `recorderctl.sh` 可避免
8. **setup.bash 硬编码编译机路径**：colcon 生成的 `setup.bash` 里 `COLCON_CURRENT_PREFIX` 指向编译时的绝对路径。目标机器上 `source ~/workspace/install/setup.bash` 需要该路径存在或用本地生成的 setup.bash。**不能只拷贝 dexe_recorder 包到全新机器**，依赖的接口包 `.so` 库也必须在 install 环境里
9. **run_recorder.sh 末尾 `wait` 阻塞 ssh**：脚本末尾 `wait "$NEW_PID"` 会导致 ssh 远程启动时挂起。用 `ssh -f` + `setsid` 脱离会话可解决
### 带宽测试（已完成）

详见 `docs/camera-bandwidth-test/` 目录下的测试报告：

- resize 话题对订阅者数量高度敏感（4订阅者降频34%）

## 七、PC2 部署调研

### 7.1 为什么部署到 PC2

手部相机（Realsense D405）连接在 PC2 上，当前架构：

- PC2 本地发布 `/camera_l/color/image_rect_raw`、`/camera_r/color/image_rect_raw`
- PC1 跨机订阅这两路话题（DDS 跨机通信）

将 dexe_recorder 部署到 PC2 的优势：

- 手部相机数据**本地订阅**，无跨机延迟和带宽消耗
- 头部相机 `/camera/kfc_compressed` 和关节状态 `/feedback/robot_server_state` 从 PC1 跨机订阅（compressed 话题实测跨机无降频）
- 充分利用 PC2 的 Jetson Orin NX GPU 硬件编码能力

| 设备      | Jetson Orin NX（与 PC1 同型号）                                             |
| ROS2      | Humble + CycloneDDS                                                         |
| GStreamer | 1.20.3 + nvjpegdec/nvv4l2h264enc（硬件插件可用，与 PC1 一致）               |

### 7.5 部署流程

> **重要前提**：目标机器的 `~/workspace/install/` 必须已存在且包含 dexe_recorder 的依赖包（end_effector_interfaces、dexe_interfaces、std_srvs 等）。这些是 ROS2 接口库，dexe_recorder 运行时需要加载它们的 `.so` 文件。全新机器需先部署完整的 install workspace。

#### 第一步：PC1 编译打包

```bash
cd ~/w1/dexe_recorder
./build.sh                    # 编译，生成 release/install.tar.gz
```

#### 第二步：传输到目标机器

```bash
# 示例：部署到 192.168.18.77（端口 5021）
scp -P 5021 ~/w1/dexe_recorder/release/install.tar.gz dexforce@192.168.18.77:~/workspace/
```

#### 第三步：目标机器上解压到 install 目录

```bash
# install.tar.gz 内部结构是 install/dexe_recorder/...
# 需要解压到 ~/workspace/install/ 下，让 dexe_recorder 合并进去
cd ~/workspace
tar xzf install.tar.gz -C install/   # 解压后：install/dexe_recorder/
```

> **注意**：如果 `install/install/` 出现了（tar 多套了一层），执行 `cp -r install/install/dexe_recorder install/ && rm -rf install/install` 修正。

#### 第四步：执行 deploy.sh 完成部署

```bash
cd ~/workspace/install/dexe_recorder/share/dexe_recorder
chmod +x deploy.sh
./deploy.sh
```

`deploy.sh` 会：
- 把 `run_recorder.sh`、`recorderctl.sh`、`convert_to_hdf5.sh`、`convert_to_hdf5.py` 拷贝到 `~/workspace/dexe_recorder/`
- 把 `config/auto_recorder.yaml` 拷贝到 `~/workspace/dexe_recorder/config/`
- **自动 `chmod +x` 可执行文件**（修复 tar 解压丢失权限的问题）

## 八、HDF5 转换

录制完成后，用独立转换脚本 `scripts/convert_to_hdf5.py` 将录制数据转为与遥操兼容的 HDF5 格式。不依赖 GStreamer 编码器，直接读取已保存的 mp4/jpg 文件。

### 8.1 依赖

```bash
pip3 install h5py numpy Pillow tqdm
```

- `h5py`：HDF5 读写
- `numpy`：数组操作（h5py 依赖）
- `Pillow`：JPEG 模式读图片尺寸（VIDEO 模式不需要）
- `tqdm`：进度条（可选）

### 8.2 使用方法

```bash
# 方式1：用 shell 封装脚本（自动找到 convert_to_hdf5.py）
./convert_to_hdf5.sh <recorded_dir> [output_dir] [format]

# 方式2：直接用 Python
python3 convert_to_hdf5.py --input <recorded_dir> --output <output_dir> [--format auto|video|jpeg]
```

**参数说明：**

| 参数                           | 说明                                                       |
| ------------------------------ | ---------------------------------------------------------- |
| `recorded_dir` / `--input` | 录制数据目录（含多个 session 子目录，或单个 session 目录） |
| `output_dir` / `--output`  | HDF5 输出目录                                              |
| `format` / `--format`      | `auto`（自动检测，默认）、`video`、`jpeg`            |
| `--skip-existing`            | 跳过已存在的 HDF5 文件                                     |

**示例：**

```bash
# 自动检测格式，转换所有 session
./convert_to_hdf5.sh /home/dexforce/data/recorded_auto

# 指定输出目录和格式
./convert_to_hdf5.sh /home/dexforce/data/recorded_auto /tmp/hdf5 video

# 直接用 Python，转换单个 session
python3 convert_to_hdf5.py --input /home/dexforce/data/recorded_auto/20260708_121030 --output /tmp/hdf5 --format auto
```

### 8.3 两种录制格式对应的 HDF5 结构

| 录制格式     | HDF5 encoding | data shape              | 说明                        |
| ------------ | ------------- | ----------------------- | --------------------------- |
| VIDEO（mp4） | `mp4`       | `()` 单个 varlen blob | 直接读 video.mp4 整个字节流 |
| JPEG（jpg）  | `jpeg`      | `(N,)` varlen 数组    | 逐帧读 000xxx.jpg           |

HDF5 文件结构（与遥操 `w1_telecontrol_to_hdf5_airs.py` 兼容）：

```
session.hdf5
├── (attrs) frames, cameras, sample_rate, robot_type, ...
├── camera_head_left/
│   ├── (attrs) encoding="mp4"或"jpeg", width=1920, height=1080
│   ├── data         # video: shape=() blob; jpeg: shape=(N,) 数组
│   └── timestamps   # shape=(N,), uint64 纳秒
├── camera_head_right/  (同上)
└── joints/
    ├── (attrs) columns=["ANKLE", "KNEE", ...]
    ├── data         # shape=(N, num_joints), float32
    └── timestamps   # shape=(N,), uint64 纳秒
```

### 8.4 验证 HDF5 文件

```bash
python3 -c "
import h5py, json
hf = h5py.File('<session>.hdf5', 'r')
print('frames:', hf.attrs['frames'])
print('cameras:', json.loads(hf.attrs['cameras']))
for cam in json.loads(hf.attrs['cameras']):
    g = hf[f'camera_{cam}']
    print(f'  {cam}: {g.attrs[\"encoding\"]}, {g.attrs[\"width\"]}x{g.attrs[\"height\"]}, data={g[\"data\"].shape}')
print('joints:', hf['joints']['data'].shape)
hf.close()
"
```

### 8.5 脚本位置

- 源码：`scripts/convert_to_hdf5.py` + `scripts/convert_to_hdf5.sh`
- 部署后：`install/dexe_recorder/share/dexe_recorder/convert_to_hdf5.py`（编译时自动打包）
- PC2 上：`workspace/convert_to_hdf5.py` + `workspace/convert_to_hdf5.sh`（部署时拷贝到 workspace 根目录）
