# 反馈录制设计文档

## **1\. 背景**

遥操作训练数据除了"命令"（pose\_record）之外，还需要记录"反馈"——即机器人各关节的**真实位置**。这部分数据用于：

- 校验命令与实际执行的差异（控制误差分析）；

- 作为 VLA 训练的观测输入（state / proprioception）；

- 离线回放与诊断。



反馈来自两条不同频率的 ROS 话题：

|话题|内容|频率|
|---|---|---|
|`/feedback/robot_server_state`|全身关节位置（JSON String，`joint_position` 数组）|\~100Hz|
|`/feedback/ee/{left,right}`|末端执行器关节位置（`EEFeedback.joint_states`，每项含 `name`\+`position`）|\~20Hz|

两条流频率不同、来源不同，但最终需要合并到**同一条 30Hz 时间线**上，作为统一的反馈帧序列落盘。



## **2\. 设计目标**

1. 反馈帧独立于命令帧的时间线——命令帧由 IK 循环驱动（受 `process_every_n_frames` 抽帧影响），反馈帧按墙钟 30Hz 稳定产出，不随 IK 抖动。

2. 100Hz 的 robot\_state 自然**抽帧**到 30Hz（每 \~33ms 取最新一份，丢弃中间帧）。

3. 20Hz 的 ee 自然**插帧**到 30Hz（两个采样点之间用上一帧的值重复填充）。

4. 回调线程不做磁盘 I/O，只更新内存快照；落盘由独立写线程完成。

5. **流式落盘**：每帧写完立即 \`flush\`，内存只留当前帧，session 不论多长内存占用恒定；进程崩溃只丢最后一帧，不丢整段 session。

6. 输出格式仿 `pose_record_*.json`：单 session 单 JSON 文件，`{session_id, frames:[...]}` 结构。

7. 反馈录制与命令录制（pose\_record）共享 session 生命周期，但写盘相互独立。



## **3\. 架构总览**

```Python
ROS 回调线程                              写线程（30Hz）
─────────────                            ─────────────
/feedback/robot_server_state (100Hz)     每 33ms 取两条流
        │                                  最新快照，组装一帧
        ▼                                  立即写盘 + flush
 update_robot_state()                           │
        │                                       ▼
        ▼                                  _emit_one_frame()
 robot_state 快照                                │
 (内存, 加锁)                                    ▼
                                         写入 feedback_record_{session}.json
/feedback/ee/{left,right} (20Hz)               （每帧一行，flush 落盘）
        │
        ▼
 update_ee_state()
        │
        ▼
 ee_state 快照 (内存, 加锁)
```

**核心设计：**回调只更新内存快照，**写线程按墙钟取快照并流式落盘**。 这样 100Hz 自然被抽帧（写线程两次取快照之间 ROS 来了 \~3 条消息，只保留最新一份），20Hz 自然被插帧（写线程取快照时 EE 还没来新消息，就用上一份）。每帧写完即 \`flush\`，内存只保留当前正在组装的一帧，session 无论持续多久内存占用恒定。



### **3\.1 流式写入机制**

JSON 文件不是 `stop()` 时一次 `json.dump`，而是分三阶段手写：

|阶段|时机|写入内容|
|---|---|---|
|头部|`start()`|`{\n  "session_id": ...,\n  "start_time": ...,\n  "target_fps": ...,\n  "frames": [`|
|帧体|`_emit_one_frame()` 每次调用|首帧前无分隔符；后续帧前补 `,\n`，再写 `    {frame...}`，`flush`|
|尾部|`stop()`|`\n  ],\n  "end_time": ...,\n  "frame_count": N\n}\n`|

**分隔符前置**（每帧写之前若非首帧补逗号）而非后置，避免尾逗号，\`stop\(\)\` 时无需 seek 回退修正。\`end\_time\` 和 \`frame\_count\` 在 \`stop\(\)\` 时写入尾部，准确反映实际录制结果。



## **4\. 关键组件**

### **4\.1\`FeedbackRecorder\`（\`src/backend/utils/recorder\.py\`）**

底层录制器，负责内存快照管理 \+ 30Hz 写线程 \+ 落盘。

**内存快照**（由各自回调更新，写线程读取，\`\_snapshot\_lock\` 保护）：

|字段|类型|更新方|说明|
|---|---|---|---|
|`_robot_state`|`Dict[str, float]`|`update_robot_state()`|全身关节名→位置，最新一份|
|`_robot_state_ts`|`Optional[float]`|`update_robot_state()`|该快照的来源时间戳|
|`_ee_state`|`{"left": {...}, "right": {...}}`|`update_ee_state()`|各手末端关节名→位置|
|`_ee_state_ts`|`{"left": ..., "right": ...}`|`update_ee_state()`|各手快照来源时间戳|

**写线程**（\`\_writer\_loop\`）：

- 按 `_sample_interval = 1/target_fps`（默认 33ms）墙钟触发；

- 每次调用 \`\_emit\_one\_frame\(\)\`：取两条流最新快照（浅拷贝），组装成一帧，**立即 \`write\` \+ \`flush\` 落盘**（不缓冲在内存）；

- 若严重落后（被挂起），重新对齐到当前时间，避免追帧风暴。

**生命周期**：

- `start(session_id)`：清空快照，打开文件并写 JSON 头部（`{`, `session_id`, `start_time`, `target_fps`, `"frames": [`），启动写线程；

- `stop()`：停写线程，补写 JSON 尾部（`]`, `end_time`, `frame_count`, `}`），关闭文件。



### **4\.2\`feedback\_recording\.py\`（\`src/backend/recording/\`）**

薄包装层，提供四个无状态函数，被 `pose_server` 和 `recording` 包内共同调用。之所以放在 `recording/` 而不是 `pose/`，是因为它被两个包引用，避免 `pose` → `recording` 的反向依赖。

|函数|调用方|作用|
|---|---|---|
|`update_feedback_robot_state(recorder, positions)`|`pose_server` 的 ROS 回调|更新全身关节快照|
|`update_feedback_ee_state(recorder, hand, joint_states)`|`EEFeedbackCollector._on_feedback`|更新单手末端关节快照|
|`start_feedback_recorder(recorder, session_id)`|`button_controller` 会话开始|启动 30Hz 写线程|
|`stop_feedback_recorder(recorder)`|`session_controller` / `button_controller` / `pose_server`|停写线程并落盘|



### **4\.3\`EEFeedbackCollector\`（\`src/backend/end\_effector/collector\.py\`）**

原有职责是订阅 \`/feedback/ee/\*\` 和 \`/feedback/tactile/\*\` 做触觉录制。新增对**关节状态**的转发：

- 构造时通过 `joint_feedback_recorder=` 参数注入 `FeedbackRecorder`；

- `_on_feedback()` 在设备识别之后、触觉处理之前，调用 `_serialize_joint_states(msg)` 把 `EEFeedback.joint_states` 序列化为 `[{name, position}, ...]`，再喂给 `recorder.update_ee_state(hand, ...)`；

- 仅 `/feedback/ee/*` 链路带关节状态（`/feedback/tactile/*` 通常无 joint\_states），故只对该链路转发。

`_serialize_joint_states` 只取 `name` 和 `position` 两个字段，不录制 `velocity`/`current`/`temperature`。



### **4\.4\`RecordingManager\`（\`src/backend/recording/recording\_manager\.py\`）**

在创建录制组件时，按 `teleop_config.yaml` 的 `feedback_record` 配置创建 `FeedbackRecorder` 并持有为 `self.feedback_recorder`，同时注入给 `EEFeedbackCollector` 和 `button_controller` / `session_controller`。



## **5\. 数据流详解**

### **5\.1 robot\_state 流（100Hz → 30Hz 抽帧）**

```Plain Text
ROS /feedback/robot_server_state (String, ~100Hz)
  │  pose_server.cb():
  │    json.loads(msg.data) → joint_position[]
  │    按 joint_keys 映射 → positions: Dict[str,float]
  │    feedback_lock 下更新 self.feedback_positions
  │    update_feedback_robot_state(recorder, positions)
  ▼
FeedbackRecorder.update_robot_state():
  _snapshot_lock 下替换 _robot_state + _robot_state_ts
  （不写盘，纯内存）
```

写线程每 33ms 取一次 \`\_robot\_state\`，期间 ROS 来了约 3 条消息但只保留最新一份 → **100Hz 被抽帧到 30Hz**。



### **5\.2 ee 流（20Hz → 30Hz 插帧）**

```Plain Text
ROS /feedback/ee/{left,right} (EEFeedback, ~20Hz)
  │  EEFeedbackCollector._on_feedback():
  │    _update_ee_info(hand, ee_name)  # 设备识别
  │    _serialize_joint_states(msg) → [{name, position}, ...]
  │    recorder.update_ee_state(hand, joint_states)
  ▼
FeedbackRecorder.update_ee_state():
  提取 {name: position} → _snapshot_lock 下替换 _ee_state[hand]
  （不写盘，纯内存）
```

写线程每 33ms 取一次 \`\_ee\_state\`。EE 20Hz 每 50ms 来一条，写线程 33ms 取一次 → 约一半的帧会重复上一份 EE 快照 → **20Hz 被插帧到 30Hz**（零阶保持）。



### **5\.3 合帧**

`_emit_one_frame()` 同时取 robot\_state 和 ee 的最新快照，组装为一帧：

```JSON
{
  "frame_id": 0,
  "timestamp": 1783410048.568,
  "robot_state": {"ANKLE": 0.12, "KNEE": -0.34, *...*},
  "robot_state_ts": 1783410048.565,
  "ee": {
    "left": {"T_MCP": 0.0, "T_CMC_YAW": 0.0, *...*},
    "left_ts": 1783410048.540,
    "right": {"T_MCP": 0.0, *...*},
    "right_ts": 1783410048.540
  }
}

```

> 每个 \`\*\_ts\` 字段记录该路快照的来源时间戳，便于离线分析时判断该帧的 robot\_state / ee 各自新鲜度。

> 



## **6\. 输出格式**

### **6\.1 文件**

`{output_dir}/{file_prefix}_{session_id}.json`

默认：`data/feedback/feedback_record_20260707_153000.json`

单 session 单文件，**流式写入**：\`start\(\)\` 时打开文件并写 JSON 头部，每帧立即 \`write\` \+ \`flush\` 落盘，\`stop\(\)\` 时补写尾部并关闭。无需临时文件 / \`os\.replace\`——每帧都已落盘，崩溃只丢最后一帧，不会留下"名字正确但内容损坏"的文件。\`flush\` 只推到 OS 缓冲（进程崩溃不丢），不做 \`fsync\`（避免 30Hz 磁盘同步开销，断电仍可能丢最后几帧，可接受）。





### **6\.2 结构**

```JSON
{
  "session_id": "20260707_153000",
  "start_time": 1783410048.500,
  "end_time": 1783410050.200,
  "frame_count": 51,
  "target_fps": 30.0,
  "frames": [
    {
      "frame_id": 0,
      "timestamp": 1783410048.533,
      "robot_state": {"ANKLE": 0.12, "KNEE": -0.34, "BUTTOCK": 0.05, "ARM_L1": 0.5, *...*},
      "robot_state_ts": 1783410048.530,
      "ee": {
        "left": {"T_MCP": 0.0, "T_CMC_YAW": 0.0, "IF_MCP_PITCH": 0.0, *...*},
        "left_ts": 1783410048.510,
        "right": {"T_MCP": 0.0, *...*},
        "right_ts": 1783410048.510
      }
    },
    *...*
  ]
}
```



### **6\.3 与 pose\_record 的关系**

|维度|pose\_record\_\*\.json|feedback\_record\_\*\.json|
|---|---|---|
|内容|下发的命令（IK 结果 \+ 手势 \+ 夹爪）|机器人真实反馈位置|
|时间线|IK 循环帧率（受抽帧影响）|独立 30Hz 墙钟|
|触发|`record_write_enabled` 时每 IK 帧|30Hz 写线程，session 期间持续|
|结构|`{frames:[{frame_id, timestamp, data:{...}}]}`|类似，但 `data` 拆为 `robot_state` \+ `ee`|

两者共享同一 `session_id`，可按时间戳或 frame\_id 对齐做命令\-反馈对照分析。



## **7\. 配置**

`config/teleop_config.yaml`：

```YAML
robot:
  feedback_record:
    enabled: true                       # 是否启用反馈录制
    output_dir: "data/feedback"         # 输出目录
    file_prefix: "feedback_record"     # 文件名前缀
    target_fps: 30.0                    # 写线程目标频率
```

- `enabled: false` 时 `RecordingManager` 不创建 `FeedbackRecorder`，`self.feedback_recorder = None`，所有 `update_*` / `start/stop` 函数判空跳过。

- `target_fps` 调整写线程频率；调高则更接近原始 100Hz（磁盘占用增大），调低则更省空间但抽帧更狠。



## **8\. 生命周期**

```Plain Text
session 开始 (button_controller.handle_record_button_press)
  │  data_manager.start_recording() → session_id
  │  start_feedback_recorder(recorder, session_id)  ← 启动写线程
  ▼
session 进行中
  │  ROS 回调持续 update_robot_state / update_ee_state（只更新内存）
  │  写线程 30Hz 取快照 → 流式写盘 + flush
  ▼
session 结束 (stop_recording_if_active / shutdown / client_disconnected)
  │  stop_feedback_recorder(recorder)
  │    └ 停写线程 → 补写 JSON 尾部 → 关闭文件
  ▼
完成
```

**停止路径有三处**，确保异常退出也能落盘：

1. `button_controller` / `session_controller`：正常停止录制；

2. `pose_server.handle_pose`：用户松开双使能（退出遥操作）时停止；

3. `pose_server.shutdown`：服务器关闭时兜底停止。



## **9\. 线程模型**

|线程|数量|职责|
|---|---|---|
|ROS 回调线程（`MultiThreadedExecutor`）|1|跑 `_joint_feedback_node` \+ `_ee_feedback_node` 的回调，更新 `feedback_positions` 和 `FeedbackRecorder` 内存快照|
|FeedbackRecorder 写线程|1|30Hz 墙钟驱动，取快照组装帧并流式写盘 \+ flush|
|主事件循环（asyncio）|1|WebSocket / IK / 录制控制|

**线程安全**：\`\_snapshot\_lock\` 保护快照读写（ROS 回调写、写线程读）。文件句柄 \`\_fp\` 只在写线程（session 中）或主线程（\`stop\(\)\` 时已 join 写线程）访问，无需文件锁。ROS 回调和写线程之间只通过 \`\_snapshot\_lock\` 交互，无其他共享可变状态。

**内存占用**：只保留当前快照（最新一份 robot\_state \+ ee）和正在组装的一帧，session 无论多长内存占用恒定（约几 KB）。



## **10\. 边界情况**

### **10\.1 录制开始前的消息**

`update_robot_state` / `update_ee_state` 有 `if not self._is_recording: return` 守卫。session 开始前 ROS 已在回调，但这些消息被丢弃（符合预期——只录 session 内的反馈）。



### **10\.2 第一帧快照为空**

session 刚启动时，写线程可能在第一条 ROS 消息到达前就触发一帧，此时 `robot_state` / `ee` 为空字典 `{}`。这些帧仍会写入，`*_ts` 为 `null`，离线分析时可按 `ts is null` 过滤。



### **10\.3 单手 EE 未识别**

`EEFeedbackCollector._on_feedback` 在设备识别前 \`info is None\`，但关节状态转发在 \`info is None\` 检查**之前**执行（只要有 \`ee\_name\` 字段就转发）。因此即使触觉能力未识别，关节位置也会被录制。



### **10\.4 写线程落后**

若系统被挂起后恢复，`next_t` 远小于当前时间。`_writer_loop` 检测到 `next_t < now` 后重新对齐到 `now + interval`，避免连续追帧风暴。



### **10\.5 进程崩溃与数据完整性**

流式写入 \+ 每帧 `flush` 保证：

\- **\*\*正常 \`stop\(\)\`\*\***：文件完整（头部 \+ 全部帧 \+ 尾部），\`frame\_count\` 准确。

\- **进程崩溃（OOM / SIGKILL / 断电）**：

\- 文件有头部 \+ 已写帧，但**缺尾部**（\`\]\`、\`end\_time\`、\`frame\_count\`、\`\}\` 未写）→ 不是合法 JSON。

- 丢失的是崩溃瞬间正在写的那一帧（可能写了一半），以及之后的所有帧。

- 已写完的帧全部保留在文件里。

\- **恢复方案**：离线脚本读取后补一个 \`\]\}\` 尾部即可解析（容错解析）。或 \`stop\(\)\` 之外的兜底路径（\`shutdown\`）正常执行时仍能写出完整文件。

之所以不做 `fsync`：30Hz `fsync` 会带来显著磁盘同步开销，且断电场景概率极低；`flush` 已足够防进程级崩溃（OOM/SIGKILL），是合理的权衡。



### **10\.6\`flush\` 失败**

若磁盘满或 IO 错误导致 `flush` / `write` 抛异常，`_emit_one_frame` 捕获并 `logger.error`，`_frame_count` 仍递增（保持帧号连续），但实际文件可能缺该帧。后续帧写入会接着上一帧的位置继续（分隔符前置策略不受影响）。



## **11\. 不做的事**

\- **不做时间戳最近邻对齐**：robot\_state 和 ee 在同一帧里各自取最新快照，不做跨流时间戳匹配。若需要精确对齐，离线用 \`\*\_ts\` 字段做最近邻。

\- **不做插值**（线性/样条）：ee 的 20Hz→30Hz 是零阶保持（重复上一帧），不做平滑插值，避免引入伪信号。

\- **不录制触觉**（tactile\_states）：触觉由独立的 \`TactileRecorder\` 录制到 \`tactile\.jsonl\`，与本反馈录制正交。

\- **不录制 EE 的 velocity/current/temperature**：只录 \`name\` \+ \`position\`。
